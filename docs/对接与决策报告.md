## 2. 两类知识的注入方案与形式（核心）

### 2.0 一句话区分

- **T（语义检索）**：知识在 **agent 想起要查的那一刻**到达，是静态文本，进入历史消息、会被压缩。**动机的授予**。
- **G（编排图）**：知识住在 **harness 的表**里，每轮循环被机制性地带到决策现场，并随账本状态变化。**纪律的授予**。

### 2.1 T 条件：我交付什么、服务器怎么接

**我交付**（`dist/T/`）：
1. `skills_flat/`：16 个 skill 目录（已就位，`skills/16个任务对口skill/`）；
2. `index.json`：检索索引（每个 skill 的 name / description（取自 frontmatter）/ 类目 / 字符数）；
3. `retrieval_tool_spec.md`：检索工具行为定义（见下）。

**服务器接入**：给 agent 一个 `skill_search(query) -> top-k (name+description)` 工具，agent 再用既有的文件读取看 SKILL.md 全文。**检索实现从简**：用 index.json 做关键词/description 匹配即可——本实验的对照变量是"编排结构"而非"检索质量"，上真向量检索反而引入新变量。图开关关闭（KnowledgeGraphMiddleware off，逐字节兼容）。

**知识到达路径**：任务书（约束只出现一次）→ agent 自主决定搜不搜、读不读、听不听。

### 2.2 G 条件：不只是注入——harness 执行中的三条指导通道

**我交付**（`dist/G/`）：`graph_tbox.yaml`（编排图）+ `metaplan_view.md`（视图模板）+ 本节的注入映射。服务器侧用**已有的 KnowledgeGraphMiddleware**（组会材料确认已部署验证通过），把在线编译的输入替换为这份离线产出即可，无需新开发。

**通道 ① graph.yaml 初始编图 → 调度器查表执行（顺序与互斥的机制保证）**

| harness 环节 | 指导如何生效 |
|---|---|
| 每轮 scheduler 选节点 | `requires` 未满足的节点**不进入候选集**——A5 训练在 A2 体检完成前对 scheduler 不可见。顺序正确性是拓扑保证，不靠模型自觉（组会 tick 5 的 unlock 事件就是这个机制） |
| 多节点同时就绪 | `no_parallel` 命中 → 扣留+落痕（"单原子变更：同一时期只验证一个改动"） |
| 节点解锁时 | `informs` 触发参数回写：A3 误差结构（FP 主导/各类样本量）写入 A4/A6 的参数——防"拿任务书旧数字拍搜索范围"的脏读 |

**通道 ② meta-plan 视图每轮现渲染 → Planner 的每个决策点都站在最新账本上（持续在场）**

| harness 环节 | 指导如何生效 |
|---|---|
| 每次 Planner 模型调用 | ViewBuilder 从 graph+hypotheses 现算 ≤2000 字符视图注入 system message——**不依赖历史消息，免疫摘要压缩**（T 的 skill 文本在历史里会被压掉，G 的视图每轮重生） |
| 证据回流后 | 假说被证实/证伪 → 后验更新 → 下一轮视图里的排序、负证据区、待决点**实时变化**——指导是活的，不是一张静态地图 |
| 负证据区 | "此路不通+原因"每轮显式可见——T 没有等价机制 |

**通道 ③ 科学合规约束进验证门 → executor 的阶段收口判定（硬约束只限科学合规）**

| harness 环节 | 指导如何生效 |
|---|---|
| stage 完成判定 | 节点 verify gate 不过 → 不算 completed（如"val<500 样本未走 K 折"则 A6 不落 completed） |
| 禁改区 | 评测代码/test 标签/split_manifest 的修改被拦+留痕 |
| 计划文本 | "阈值只在 val 选"写进 graph constraints，每轮视图重申 |

**不反客为主（软引导护栏，组会已定原则）**：Planner 可提议图外新假说（走正常裁决）；优先级判断归 Planner/E9；硬拦截只限科学合规三件事（验证门/禁改区/no_parallel）。**图给地图，不画铁轨。**

## 3. 服务器跑批方式（决策定稿建议）

### 3.1 顺序跑，不并行——理由

| 方案 | 判定 | 理由 |
|---|---|---|
| 同一 tbox 顺序跑两次×3 | **采用** | 初始状态完全一致（每次跑前 git 复位）；无资源争抢；轨迹干净 |
| 复制一份 tbox 并行 | 不采用 | ① 同机并行抢 GPU/CPU/网关配额，wall-clock 与重试行为被扭曲——污染的是我们的判定族指标本身；② 两套 run 在同一项目仓里操作 git 分支会互相看见（plan 分支/worktree 冲突）；③ 省下的是几个小时，赔上的是可比性 |

### 3.2 配对与顺序

- **交替顺序**：T1 → G1 → T2 → G2 → T3 → G3（不连跑同一条件），消除时间漂移（模型端更新、服务器状态、网关窗口）；
- **每次跑前环境复位**：tbox 工作区 `git reset --hard <固定 commit>` + `git clean -fd` + 删旧 plan 分支——保证每个 run 的初始状态逐字节一致；
- **run 配置**：`max_trials=3`，预算封顶；模型/温度/工具白名单两边一致；
- **时长估计**：v2 冒烟单 trial 约 47 分钟；`max_trials=3` 估 1.5–3h/run，6 个 run 顺序跑约 1–1.5 天，可接受。

### 3.3 "短 run 看不出优势还是反而能看细节"——明确回答

**两者都对，取决于看哪族指标**：

- **终点指标（recall/neg_recall/f1）**：n=3 + 短 run，差异**就是噪声**，只记录不判定——组会已有同口径结论（0.881±0.021 vs 0.912±0.008，差异在方差不在均值）；
- **过程/治理指标（判定族）**：短 run 恰恰是**优势**——轨迹短到可以**逐决策点精读**。分析方法：每个 run 产出"决策点标注表"（每个分支选择点：选项/选择/依据/是否引用指导信息/是否正确），T/G 并排对照。信息缺失事故、盲抄 skill、test 泄漏、单原子变更违规这些指标在单次 run 内就是**计数型证据**，不需要大样本；
- 组会的剧本级数据（分支正确率 1.0 vs 0.83、事故 0 vs 2）就是这个粒度的证据，本实验把它搬到真实任务 + harness 统一账本口径下复验。
